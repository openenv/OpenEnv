# Security Policy

## Supported Versions

We ship security fixes in the latest release of `openenv` on PyPI, and the environments under `envs/` are fixed on `main`. Please reproduce on the current release or on `main` before reporting. We do not backport fixes to older releases. Environments deployed from older sources (Hugging Face Spaces, images built from `envs/*/server/Dockerfile`) get a fix only when they are redeployed.

## Reporting a Vulnerability

Report privately. **Do not open a public issue, pull request or discussion for a suspected vulnerability.**

Use GitHub private vulnerability reporting: the **"Report a vulnerability"** button under this repository's [**Security**](https://github.com/openenv/OpenEnv/security) tab. It reaches the maintainers, keeps the report private until a fix is released, and lets us work on the fix with you in a private fork and issue a CVE through GitHub when warranted.

Never put real tokens or keys in a report or a proof of concept. Use fake ones. If a real secret may have leaked, rotate it first.

## Recognition

We do not offer a monetary bounty. For a valid, in-scope report we credit you on the published GitHub Security Advisory and as the reporter in the associated CVE. Tell us how you would like to be credited (name or handle).

## What your report must include

Copy this block into your report and fill in every field. Reports without the version, the proof of concept or the impact are returned as incomplete.

```markdown
### Summary
One sentence: what the vulnerability is and where.

### Affected version / commit
Exact released version or commit SHA you reproduced on (e.g. 0.14.0 / a1b2c3d).
Not "latest" or "main".

### Affected component
The package API, CLI command, server endpoint or environment involved
(e.g. `create_app`, `/ws`, `openenv push`, `envs/repl_env`).

### Vulnerability class
Type and CWE if known (e.g. path traversal / CWE-22, SSRF / CWE-918).

### Attack vector & preconditions
- Who is the attacker and what do they control (a client of an env server,
  the model's output, a task or dataset, a file)?
- What must be true for the attack to work (a secret set on the server,
  a non-default setting, a public deployment)?

### Proof of concept
A minimal script or step sequence that runs on a clean install or a
deployment you own, with fake credentials. Include the exact commands, and
the expected vs. the actual behavior.

### Impact
What an attacker gains in a realistic deployment.

### Scope
Which trust boundary below does this cross?

### Suggested severity (optional)
We assign the final severity. Include a CVSS v3.1 vector only if you have one.

### Suggested fix (optional)
```

> The bar is a **reproducible PoC against a supported version, with a concrete impact that crosses a trust boundary listed below**. Reports that are theoretical, generated by a scanner or an LLM without a verified chain, or that restate documented behavior are closed without detailed review.

## Threat model & trust boundaries

**Clients of an environment server are not trusted.** An environment server is a plain HTTP and WebSocket service. When it is reachable (for example on a public Space), anyone can call `reset`, `step`, the MCP tools and the web UI, and everything they send (reset parameters, actions, tool arguments) is untrusted. A client that makes the server use its own credentials, read or write files outside what the environment is for, or run commands it is not meant to run crosses this boundary. Floods and load on a server you exposed are a deployment concern (see the optional request guard in the docs), not a vulnerability.

**The model's output is not trusted.** Environments that run code or commands the model writes (Python, shell, other languages) must keep the server's secrets out of that code's reach, and must keep one session from reading or changing another. Running that code, with the files and tools the environment documents, is the purpose of the environment and not a vulnerability. Reaching the server's credentials, another session, or anything an environment documents as blocked, is.

**The deployer is trusted.** Whoever runs a server chooses its configuration, its secrets, its network exposure and the tasks and datasets it loads. Loading a task, dataset or environment image you did not create is a trust decision, like loading any other code.

**The CLI is an operator tool.** Commands you run yourself (`openenv init`, `push`, `build`, `serve` and the harbor commands) act with your permissions on inputs you chose. They are in scope only when they expose your credentials or act on something you did not ask for.

## In scope

- Code in the `openenv` package and the environments under `envs/` crossing one of the boundaries above.
- Exposure or mishandling of credentials or tokens by OpenEnv code, including secrets ending up in logs, observations, trajectories or uploaded datasets.
- A protection an environment documents (an allowlist, a blocked syscall, a path check, a sandbox) being bypassed.
- CI/CD or supply-chain issues in this repository.

## Out of scope

- Deployments that someone else operates (Spaces and servers not run by the maintainers). Report those to their owner. Do not test against them.
- Findings in `examples/`, documentation and tests. Report them as normal issues or pull requests.
- Denial of service against a server you run yourself, absent an impact on other sessions or tenants.
- Model behavior: jailbreaks, prompt injection, harmful generations or reward hacking that stays inside what the environment allows.
- Vulnerabilities in third-party dependencies we do not vendor. Report them upstream.
- Theoretical issues without a working proof of concept, and best-practice or hardening suggestions without a demonstrated impact.

## Safe harbor

Good-faith research that respects these guidelines, avoids privacy violations and service disruption, and gives us a reasonable disclosure window will not be pursued by us. Use your own deployments and fake credentials, and do not access data that is not yours.
