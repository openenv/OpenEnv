Black-Box: Train Real Agents with Harbor

Some agents can’t be reimplemented as a trainer’s tool loop. A coding agent such as OpenCode, Claude Code or Codex has its own planner, tools, context management and stop condition, and the point is to train the model that drives that agent. This is the black-box harness path: the agent owns its loop, and OpenEnv records every model call it makes. Episodes are tasks: an instruction goes in, the agent works on its own, and a verifier checks the result. If the job is a conversation instead, or the agent has to use your environment’s own tools, see Evaluate Claude Code in an Environment. Harnesses in OpenEnv compares the paths.

OpenEnv does this through Harbor, which supplies the tasks, the sandboxes, the agents and the verifiers. One harbor_env server runs any of 16 validated agents on any Harbor dataset, in any of Harbor’s sandbox backends, and its capture proxy returns the token ids and logprobs of each model call together with the task’s reward.

Try One Rollout

With an OpenAI-compatible endpoint in $LLM and Python 3.12 or later:

pip install "openenv[harbor]"

openenv harbor rollout \
  --llm-url $LLM \
  --dataset AdithyaSK/data_agent_rl_environment_eval \
  --task-index 0 --harness opencode --sandbox e2b \
  --out rollout.json

Against a hosted provider you get an evaluation rollout: the reward and the full trace. Against vLLM or SGLang you also get the token ids and logprobs that training needs. openenv harbor info checks first which agents, sandboxes and capture level this machine can use.

Before running an agent of your own, check its wiring and constructor without starting a sandbox:

openenv harbor info --harness my_package.agent:MyAgent --model org/model --json

This imports and constructs the named class with dummy capture credentials; only name code you trust. It reports errors such as a missing constructor setting or undeclared api_base/api_key, and returns exit code 1 on failure. Success confirms construction, while model calls and capture remain untested. See Your own agent for the contract.

Train on the Captures

Each rollout comes back as a TrainingTrace: the token ids, logprobs and loss masks of every model call, plus the task’s reward. It doesn’t depend on a trainer, so any framework can train on it. TRL has a worked example: HarnessAsyncGRPOTrainer, an AsyncGRPOTrainer whose rollouts are harness sessions, runs each task to completion, reads back the trace, and syncs the new weights into the same vLLM server.

  • TRL’s guide to training on harnesses explains how it works and how to wire it.
  • examples/async_grpo_harbor is the complete script, with a Hugging Face Jobs launcher.
  • The ultimate guide to multi-harness RL trains one model across four agents (OpenCode, Claude Code, Codex and Mini-SWE-Agent) and covers why the white-box loop isn’t enough, how the capture works and what the runs showed.

Record a Teacher for SFT

The trace of an evaluation rollout is also supervised data. Point --llm-url at a strong model on a hosted provider, run the agent on training tasks, and every solved task becomes one conversation of the agent working through it: system prompt, task, each assistant turn with its tool calls, and each tool output. A small model fine-tuned on those conversations is a starting point for RL, and generating them needs no GPU.

openenv harbor rollout \
  --llm-url https://router.huggingface.co/v1 --api-key $HF_TOKEN --model <teacher> \
  --dataset FineEnvs/SmolDataEnvs-harbor-train \
  --task-index 0 -n 50 --harness opencode --sandbox hf-sandbox \
  --reward-key correctness,reward --out results.json

In each result, the agent’s last model call holds the whole conversation as it was sent (request_messages) and the tools the agent offered (request_tools). That call plus its reply is one SFT row, and export-sft writes them for a batch of results:

openenv harbor export-sft results.json --min-reward 1.0 --out rows.jsonl --push-to <you>/agent-traces

Retries are left out, and so are calls the agent makes on the side, such as session titles, when the capture records them as a conversation of their own. Rollouts with an unusable capture, an empty last reply or a malformed tool call are skipped and counted. Three details decide whether the rows train well:

  • Keep only solved tasks. Every row carries the verifier’s reward, and --min-reward 1.0 keeps the correct trajectories with no labelling.
  • Type tool calls as Json. export-sft parses tool-call arguments into dicts, which chat templates such as Qwen3.5’s iterate over. Load messages and tools with the Json feature of datasets: a schema inferred from the rows, as load_dataset("json", ...) does, gives every tool call the argument names of every other tool as None, and the chat template renders them.
  • Split by data source, not by task. Many task suites build several tasks on the same files. If an evaluation task shares its data with a training task, the student has already seen its files and columns, and the evaluation overstates how well it generalizes.

TRL’s examples/sft_agent_traces runs the whole recipe on Hugging Face Jobs: a teacher generates traces on SmolDataEnvs, a 2B student trains on the solved ones with SFTTrainer, and the same harness evaluates it before and after.
